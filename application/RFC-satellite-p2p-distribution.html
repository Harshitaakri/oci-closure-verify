Overview

Harbor Satellite makes OCI images and artifacts available at edge locations. When a Satellite in an air-gapped or intermittently connected deployment misses an artifact, its only recovery paths today are a central registry, Ground Control, or manually imported offline media — even when another trusted Satellite on the same local network already holds the exact content.

This RFC proposes an opt-in trusted-peer distribution mode: a Satellite consults a configured set of trusted local peers, determines which peer holds a requested OCI artifact, and copies that artifact into its own local content store — with no Internet and no Ground Control connectivity required, and with OCI digest-based integrity preserved end-to-end.

The design rests on one structural observation and one correctness principle:

  • Structural: every Satellite already fronts an OCI Distribution API — today via embedded Zot, in the target architecture via the transparent proxy serving retained content (ADR-0009). Therefore the peer read path requires no new wire protocol. The engineering surface is peer selection, trust, and transfer correctness — not transport invention.
  • Correctness: an OCI artifact is a descriptor graph, not a manifest. "Peer has the manifest" is not "peer has the artifact," and "we fetched the manifest" is not "the artifact may become visible." The transfer engine therefore enforces closure-complete, digest-verified, root-last publication with idempotent crash recovery (§9.3–§9.4), so that a partially transferred artifact can never be observed by a consumer.

The proposal is deliberately shaped to survive the ADR-0009 transition (Crane → ORAS, Zot leaving the target architecture): peers are modeled as one more content source behind the same resolve/fetch/copy abstraction that ADR-0009 mandates, selected after local content and before (or instead of) upstream.

Motivation

Edge fleets exist precisely where connectivity is worst: retail branches, factory floors, vessels, defense sites. Operational reality in such fleets:

  1. Rollout waves are LAN-redundant. When a desired-state update adds app:v42 to 30 Satellites on one site network, today each Satellite independently pulls the same bytes across the constrained uplink — or waits for media. The first Satellite to hold the artifact could serve the other 29 at LAN speed.
  2. Air-gapped sites bootstrap by sneakernet. Content is imported to one Satellite via offline media; propagating it to N others currently means N manual imports. Trusted-peer distribution turns one import into a site-wide seed.
  3. Ground Control outages should degrade, not disable. A Satellite that misses content during a GC outage has a healthy neighbor with the bytes; the current architecture cannot use it.
  4. Bandwidth cost is asymmetric. Uplink (satellite/cellular/VPN) is expensive and slow; LAN is abundant. Every peer-served byte is an uplink byte saved.

The upstream issue (#542) and program listing name exactly this capability, and require the design to "work without Internet or Ground Control connectivity and preserve OCI digest-based integrity verification."

Goals and Non-Goals

Goals

  • G1 — An approved ADR covering architecture, trust model, failure modes, and headless/air-gapped compatibility. ADR-0010 is drafted upstream as PR #638; this document is the extended design record backing it.
  • G2 — Opt-in trusted-peer configuration model (FR1) with strict validation and fail-closed semantics.
  • G3 — Digest-addressed availability checking and closure-complete, digest-verified, root-last transfer (FR2–FR3, §9.3–§9.4).
  • G4 — Deterministic fallback chain and peer health management (FR4, §9.5).
  • G5 — First-class observability: metrics, structured logs, audit events (FR5, §9.8).
  • G6 — Multi-Satellite air-gapped integration environment with fault injection, seeded by the reference experiment (FR6, §10).
  • G7 — Operator documentation (FR8).

Non-Goals (v1)

  • N1 — Dynamic peer discovery (mDNS/DNS-SD/DHT/gossip). v1 peers are explicitly configured; discovery is future work layered on the same source abstraction (§19).
  • N2 — Untrusted or semi-trusted peers. v1 trust is binary and allowlisted.
  • N3 — WAN/cross-site federation. Scope is the local network segment.
  • N4 — Changes to signing/verification trust roots. Integrity continues to come from OCI digests; signature verification remains whatever policy the Satellite already enforces.
  • N5 — Replacing desired-state replication. The peer path is a source optimization for satisfying desired state (and, in the proxy model, cache fill) — not a new state protocol.
  • N6 — Peer-to-peer push. v1 is pull-only from the requesting Satellite's perspective; nothing is written to a peer.

Gap Analysis — what is and isn't captured upstream

Captured in #542 and community discussion

The upstream thread already contains valuable ground-truth that this design treats as constraints, credited to the contributors who established it:

  • Tag/digest divergence is real and reproducible — a mutable tag moving between desired-state recording and copy time causes the destination to receive different bytes than recorded (community reproduction by 1amKhush). B2/B3 confirm the mechanism at code level. Constraint absorbed: peer protocol is digest-only; peers are never asked about tags (§9.2).
  • The architecture is mid-transition — ADR-0009 supersedes the Crane/Zot target state, and documented Zot sync behavior was found to be gated behind build tags absent from normal builds (community archaeology by shreyashsri79). Constraint absorbed: no coupling to Zot or its sync extension; source abstraction survives the transition (§9.1).
  • BYO-registry portability matters — raised by harshal0704, whose adjacent state-semantics work (deletion states, re-added artifacts) also informs the local-store interaction. Constraint absorbed as NFR3.

What this RFC adds on top of the prior discussion

  1. The digest-domain problem (B3). Today's copy path rewrites manifest media types, so local digests can differ from source digests. No prior discussion defines which digest domain the peer path verifies against. §9.4 does, and makes the peer path digest-preserving. The source-domain half is already being corrected by the author's PR #637, which makes replication prefer the recorded digest when available — closing the moved-tag window — with a regression test covering the case.
  2. Closure-complete, root-last publication as the atomicity mechanism, with a precise definition of "closure" (including how referrers are and aren't part of it) and of "addressable" (§9.3–§9.4).
  3. Idempotent crash recovery and per-digest singleflight, extending the codebase's existing blob-presence pattern (B4) to graph scope.
  4. A trust model that extends accepted ADR-0005 SPIFFE identity instead of inventing peer identity, with an explicit threat table (§9.6).
  5. A 10-row failure-mode matrix with detection, behavior, and the observable signal for each (§11).
  6. A reproducible fault-injection experiment demonstrating the violation and the invariant on real registries, offered as the seed of the FR6 integration suite (§10).
  7. A complete configuration and observability specification consistent with existing pkg/config patterns and the audit pipeline (§9.7–§9.8).

Design

9.1 Placement — a peer is a content source (ADR-0009-native)

ADR-0009 mandates "one resolve, fetch, copy, and metadata model" for local and remote content, with oras-go as the graph-transfer substrate and policy evaluated fail-closed before content is served (B5). This design adds one new implementation of the existing concept "where content comes from":

ContentSource (concept; ORAS Target/ReadOnlyStorage in target arch)
 ├── LocalStore     — Zot today; ORAS OCI layout in target architecture
 ├── TrustedPeer    — this RFC: a configured peer's Distribution endpoint
 └── Upstream       — Harbor / configured upstream registries

Resolution order for a required digest: local → trusted peers → upstream (if reachable) → explicit failure. In the target proxy pipeline, the peer source participates in stage 3 ("allowed execution: selected source") and its fetched content flows through the same verification and policy gate as upstream content — peer-sourced bytes get no policy shortcut (see OQ6).

Two integration modes, both behind the same source:

  • Reconcile-time fill (v1 default): the state process, on a missing digest, consults peers before upstream. Smallest change; works headless.
  • On-demand fill (proxy mode): a client pull that misses locally triggers a peer-first fill. Natural in the ADR-0009 proxy; enabled second.

Because oras-go is not yet wired (B6), v1 ships as an adapter implementing today's Replicator-adjacent seam while presenting the ORAS Target-shaped interface internally — so the same engine drops into the proxy architecture unmodified.

9.2 Peer wire protocol — the OCI Distribution API, digest-only

Every Satellite already serves Distribution (B7); the peer read path is therefore plain, spec-compliant, and BYO-portable:

Operation Call Notes
Manifest availability HEAD /v2/<repo>/manifests/<digest> Digest reference only — peers are never asked about tags (constraint from Gap Analysis)
Blob availability HEAD /v2/<repo>/blobs/<digest> Used during planning and resume
Manifest fetch GET /v2/<repo>/manifests/<digest> Accept covers image + index + artifact media types
Blob fetch GET /v2/<repo>/blobs/<digest> Streamed; hashed on the wire

No custom endpoint is required for v1. A batched availability check (one request answering "which of these N digests do you hold?") is a candidate optimization once N×HEAD becomes measurable overhead — deliberately deferred and listed as OQ4, since it is the only place a Satellite-specific API would leak into the peer protocol.

9.3 Transfer engine — closure, verification, and the five invariants

Definitions.

  • The closure of a root descriptor is the set of descriptors reachable via manifest references: for an index, its child manifests and their closures; for a manifest, its config and layer descriptors. Every artifact — image, chart, SBOM, model — is such a graph (FR7).
  • Referrers (signatures/attestations attached via subject) are discovered through the referrers API, not reachable from the root, and are therefore not part of the default closure; an opt-in include_referrers expansion transfers them alongside (§19).
  • An artifact is addressable when a consumer can obtain its root manifest from the local store by tag or root digest.

Invariants.

ID Invariant
I1 Digest-preserving transfer. Every fetched byte stream is hashed on the wire and must equal the descriptor's digest and size; content is stored under exactly that digest. The peer path performs no media-type rewriting (contrast B3).
I2 Closure completeness before publication. All descriptors in the root's closure are present and verified locally before the artifact may become addressable.
I3 Root-last publication. Order: blobs → child manifests → root manifest/index last, then tag association. Children stored earlier are individually valid, digest-addressed content — never a broken artifact.
I4 Idempotent crash recovery. Presence of a verified digest is the only resume state needed; a restarted transfer re-plans the closure, skips verified content (extending B4 to graph scope), and continues. Orphaned partial content is bounded by a janitor/GC pass.
I5 Per-digest singleflight, bounded concurrency. Concurrent demands for one digest coalesce into one transfer; blob-level and transfer-level concurrency caps plus an optional bandwidth limiter honor the edge envelope (NFR4).

Engine phases: PLAN (resolve root digest from desired state; walk the graph — fetching only manifests — and diff against local presence) → FETCH+VERIFY (leaves first, streamed, hashed) → PUBLISH (root last, tag last) → DONE; with RETRY (same peer, jittered backoff) → NEXT PEER → FALLBACK (upstream) → FAIL (nothing visible) on error paths, and RESUME after crash.

9.4 Publication semantics and the digest-domain rule

B3 exposes a subtlety no prior discussion has addressed: the current replicator's media-type normalization means locally stored digests can differ from upstream digests. If Satellite A imported an artifact through that path, the digest recorded in desired state (source domain) and the digest A actually serves (local domain) may disagree — and a peer transfer that verifies against the wrong domain will either fail spuriously or, worse, "verify" the wrong expectation.

Rule proposed by this RFC: the peer path operates entirely in the descriptor domain of the root being transferred — the root digest requested is the root digest published, and every child is verified against the digest embedded in its parent. The peer path never rewrites, never re-normalizes, and never consults tags. Where desired state carries a source-domain digest that local history has rewritten, the mismatch is detected and surfaced (metric + audit event), not papered over. Longer-term, ADR-0009's ORAS copy is itself digest-preserving, which converges the domains; the peer path is simply strict from day one. A first corrective step in the source domain already exists: the author's PR #637 makes replication use the recorded image digest when present, so a moved source tag can no longer cause the wrong image to be replicated. The remaining fleet-wide interaction is raised explicitly as OQ2 because it touches replication behavior beyond this feature.

9.5 Peer selection, health, and fallback

  • Eligibility: configured allowlist (§9.7); a peer marked revoked by lifecycle state (B9), failing TLS verification, or tripping its circuit breaker is ineligible.
  • Selection: filter by availability (HEAD of root digest), then order by static priority, then by a health score (EWMA of recent latency/success). v1 keeps scoring simple and observable; no consensus, no gossip.
  • Circuit breaking: consecutive failures open the breaker for a backoff window (jittered, capped); verification failures (I1) demote immediately and emit a distinct audit event — corrupt bytes are a trust signal, not a retry signal.
  • Fallback chain: peers (in order) → upstream if configured and reachable → explicit failure with a machine-readable reason (no_eligible_peer, closure_incomplete_on_peers, verification_failed, upstream_unreachable). Silent hangs are treated as bugs.

9.6 Trust model

Trust answers availability and reachability questions ("whom may I ask; who may ask me"); integrity comes from digests (I1) and is peer-independent. This separation is what makes trusted-peer distribution safe in air-gapped fleets: a compromised peer can refuse service or serve garbage, but garbage cannot verify.

  • Transport & identity: mTLS between Satellites using the existing TLS configuration surface (cert_file/key_file/ca_file — B8). Deployments already adopting ADR-0005 get peer identity from SPIFFE/SPIRE SVIDs with no new machinery; a pre-provisioned CA bundle covers air-gapped sites that haven't. Peer identity must match the configured peer entry (no wildcard trust).
  • Authorization (v1): binary — a trusted peer may fetch any repository this Satellite serves, optionally narrowed by a repository allowlist per peer. Fine-grained per-artifact ACLs are future work.
  • Serving role is opt-in separately from fetching (serve_peers), so operators can deploy read-only leechers.

Threat table.

# Threat Mitigation
T1 Peer serves wrong/corrupted bytes I1 verification; immediate demotion + audit event; nothing published
T2 Truncated transfer (peer dies mid-blob) Size+digest check fails; retry/next-peer; root never published (I3)
T3 Peer lies about tags Impossible by construction — tags are never requested (§9.2)
T4 Stale peer (holds old content) Availability is digest-presence only; "stale" content is simply absent for the requested digest
T5 Rogue device poses as peer mTLS + allowlist + identity match (B8); revoked lifecycle excluded (B9)
T6 Trusted-but-compromised peer used for exfiltration via fetches Per-peer repository allowlist; audit trail of every served digest; serving opt-in
T7 Resource exhaustion (slow-loris peer, oversized closure) Timeouts at every phase; size ceilings from descriptor metadata; concurrency caps; breaker
T8 Replay/duplication Content-addressed and idempotent — replay is a no-op

Reference Experiment — reproducible correctness demonstration

The companion harness oci-closure-verify demonstrates both the violation and the invariants on real registries — no cloud, no cluster, three local containers — with a recorded run. Its four verified behaviors map one-to-one onto §9.3: root-visible-last publication → I3; fail-closed handling of missing manifests → I2 / matrix row 10; digest-verified corruption detection → I1 / T1; singleflight deduplication of concurrent requests → I5. The scenario set:

  1. Setup: peerA, peerC, local registries; a multi-platform artifact (index → 2 platform manifests → configs + layers, 8-node closure) seeded to peerA and peerC with crane; full closure digests recorded.
  2. Violation (naive copy): delete one platform child manifest from peerA; run a tag-first naive copy into local, publishing the index up front. Result: crane pull --platform linux/amd64 succeeds while linux/arm64 404s — a visibly broken artifact, exactly what FR3/NFR5 forbid.
  3. Invariant (engine semantics): the harness (Go, go-containerregistry) walks the closure, fetches leaves-first with on-the-wire hashing, and publishes the root last. docker kill peerA mid-blob ⇒ the root never appears in local (I3); re-run resumes against peerC, skipping verified blobs (I4); crane validate green.
  4. Corruption: flip one byte of a blob on the peer ⇒ digest mismatch, transfer aborts, nothing published, peer demoted (T1).
  5. Concurrency: two simultaneous requests for the same digest coalesce to one transfer (I5).

The harness is deliberately shaped to become the seed of the FR6 multi-Satellite air-gapped e2e suite (extending test/e2e/, B11), so the application-time artifact converts directly into term deliverable work.

Performance & Resource Envelope

  • Throughput is LAN-bound; the CPU cost is dominated by SHA-256 on the wire (hundreds of MB/s per core on typical edge x86/ARM — to be measured in the experiment transcript).
  • Memory is O(blobs_per_transfer × stream-buffer): streaming I/O end-to-end, no whole-blob buffering (NFR4).
  • Disk during transfer is bounded by artifact size + staged-but-unpublished content, reclaimable by the janitor (I4).
  • Availability checking costs one HEAD per unresolved digest per candidate peer, LAN-local; the batched check (OQ4) is the escape hatch if fleets make this measurable.
  • When disabled, the feature contributes zero goroutines, zero sockets, zero config surprise (FR1).

Alternatives Considered

Alternative Why not
Custom P2P transfer protocol Reinvents Distribution semantics; loses BYO portability; enlarges the security surface for zero capability gain — peers already speak Distribution (B7)
Zot sync extension as the mechanism Couples to a component leaving the target architecture (B5); tag/period-oriented; build-tag availability caveats (Gap Analysis)
Node-level cache (Spegel-style) Ephemeral, cluster-internal semantics; Satellite requires durable, auditable registry import that survives node churn and works without k8s
DHT/IPFS content network Open-world discovery contradicts allowlisted air-gap trust; operationally heavy on edge hardware
Do nothing (status quo) U1–U4 costs persist; the listing's air-gap requirement is unmet
Publish-then-verify (optimistic import) Violates NFR5/I3; the experiment's violation demo (§10.2) is exactly this failure made visible

Operations

  • Enablement: per-Satellite config flag, default off; canary one peer pair, then widen. Disable is instant and safe (in-flight transfers abort; nothing partially visible; staged content GC'd).
  • Downgrade: no schema/state migrations; removing config restores prior behavior bit-for-bit.
  • Troubleshooting: every failure row in §11 maps to a metric + log event; the doc set (FR8) includes a symptom→signal table and a satellite peers status-style diagnostic (CLI surface to be aligned with existing cmd/ patterns).
  • Fleet hygiene: peers in revoked lifecycle are excluded automatically (B9); operators rotate peer TLS material through the same channels as existing Satellite TLS (B8).

Security / Privacy / Compliance

  • Supply-chain integrity: unchanged trust root — content identity is the OCI digest; peers add availability, not authority (§9.6). Signature/attestation graphs can travel with content via the referrers expansion without new verification semantics (N4).
  • Transport: mTLS peer↔︎peer; identity pinned to configured peer entries; SPIFFE-ready (B8/ADR-0005).
  • Auditability: every import records source peer, digest, outcome through the existing audit sinks (B10) — the compliance story for air-gapped sites is "every byte's provenance is logged and hash-verified."
  • Privacy: no new data classes; peer traffic stays on the local segment; no telemetry leaves the site that doesn't already.
  • Egress posture: the feature reduces WAN egress and introduces none of its own.

Risks

Risk Mitigation
ADR-0009 churn lands mid-term and moves the store/copy substrate The source abstraction (§9.1) is the seam; engine logic (closure/verify/publish) is substrate-independent; deliverables sequenced so the ADR settles interfaces first
Review bandwidth on a fast-moving repo ADR-first process; small PRs mapped to §13 phases; e2e evidence attached to each
Zot behavioral variance / removal timing Distribution-primitives-only baseline (NFR3); store behind a seam
Peer misconfiguration at fleet scale Fail-closed validation (§9.7); explicit reasons; docs symptom table
Scope creep toward discovery/federation Non-goals N1/N3 enforced; future-work parking lot (§19)
Digest-domain interactions with legacy imports (B3) Strict rule + detection metric (§9.4); surfaced as OQ2 rather than silently decided

Future Work

  • Batched availability API (OQ4) once HEAD fan-out is measurable.
  • Peer discovery (mDNS/DNS-SD; SPIFFE-federated attestation) layered on the same source abstraction.
  • Referrers-aware default policies (e.g., "always carry signatures for repos matching X").
  • Cross-site federation over intermittent WAN with scheduling/backpressure.
  • Bandwidth-aware plan splitting across multiple peers per closure (matrix row 5 formalized into an optimizer).
  • Policy-differentiated peers (per-peer artifact-type or namespace policies) under the ADR-0009 policy engine.
